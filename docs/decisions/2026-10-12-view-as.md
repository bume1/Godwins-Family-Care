# "View as" for the Super Admin (owner request, 2026-10-12)

Owner ask: test what every role sees and can do without keeping 20 test logins. Owner answers: **full act-as**, **Super Admin only**, **never into another admin**.

- **It is a session, not a token trick.** `POST /api/admin/impersonate/:userId` (`requireAdmin`) creates a session row whose `userId` is the person viewed, plus `impersonatorId`, `impersonatorName`, `impersonatorSid`. `authenticateToken` rebuilds `req.user` from that person's fresh record, so the admin sees exactly what they see. The rules live in one module, `impersonation.js`.
- **Refused:** a non-admin, an admin target (`ACTING_AS_ADMIN_REFUSED`), yourself, an inactive account, a nested start, and (with MFA enforced) an admin session that never passed MFA.
- **Tied to the admin's own session.** Every request checks the admin's session (`impersonatorSid`), which also keeps it from going idle. Admin signs out → the view dies (`AUTH_REVOKED`, `acting_as_admin_signed_out`). Admin demoted or deactivated, or the viewed account made an admin → dies on the next request. Hard 60-minute cap.
- **Three things stay blocked, and a later session must not open them:**
  1. **Signatures in someone else's name.** `BLOCKED_WHILE_ACTING_AS` lists every sign, co-sign, addendum, prescription, care plan, consent, ROI, packet, attestation, standing order and result acknowledgement route. Refused inside `authenticateToken` with `ACTING_AS_BLOCKED` (a 403 that is NOT an `AUTH_` code, so nobody is signed out). A test sweeps every signature-shaped route the server registers and fails if one is missing from the list.
  2. **OpenEMR.** Tokens are per user, so acting as a clinician would write into the chart under their name. `emrTokenProvider` in `server.js` refuses (`EMR_BLOCKED_WHILE_ACTING_AS`) when the request context carries an impersonator. Every EMR call passes through it.
  3. **Their account:** password, authenticator, OpenEMR connection.
- **Emails still send.** The banner says so.
- **Audit:** every row written during a view carries `impersonatorId`/`impersonatorName` (top level and in `details.actingAsBy*`), including `phi_access`. `impersonation_started` and `impersonation_ended` are their own rows.
- **Browser:** View as buttons on the User Management list and in the Edit User form's Account recovery card (Super Admin only, never on an admin or inactive row). The hub stashes the admin's tokens in `localStorage` `gfc_view_as_return`, writes the viewed person's token into all three keys and goes where their login would (`appLinks.homeFor`). `session-guard.js` (on every signed-in page) shows a gold banner from the heartbeat's `actingAs` and an Exit button; Exit, the 60-minute cap and any sign-out restore the admin tokens and return to `/admin`.
- **Verified:** `test/impersonation.test.js` (15), 11 of 11 mutations caught; `scripts/verify_impersonation.js` 33/33 through the real HTTP routes with MFA on (caregiver, client and clinician views; every refusal; exit; admin sign-out; mid-session demotion; audit rows read back); full suite 2026 pass, 0 fail; admin hub compiles; driven in Chromium: click View as, caregiver app with the banner, Exit back to the hub with the admin token restored. One existing guard repointed: the heartbeat now also returns `actingAs`.
- **Open for the owner:** you still need one account per role to view as. A seeded set of test personas for dev is a separate, small job if wanted.
