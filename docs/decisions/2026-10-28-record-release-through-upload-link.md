# The provider record release (Transfer-of-Care ROI) can be signed through the no-login upload link

Owner request, 2026-10-28: "move the provider ROI release wizard into their unique link area, so they can be submitted via the unique link AND via the enrollment wizard."

- **Both doors stay.** The portal still offers the release right after enrollment ("You're enrolled!" → Authorize Release) and from Documents. The upload link (`/upload/:token`) now has a **Sign a Record Release** card under the document checklist, with the same two choices: fill it out and sign on screen, or upload a signed scan.
- **One handler, two doors.** `handleRoiSubmit` and `handleRoiUpload` in `server.js` hold everything the portal routes did. The portal routes call them with the session; the link routes (`GET /api/gfc/upload/:token/transfer-roi`, `POST …/transfer-roi/submit`, `POST …/transfer-roi/upload`) call them with the token. Every 45 CFR 164.508 check, the render-before-write rule, the 42 CFR Part 2 opt-in, the Drive copy, the admin email and the prior-provider merge are therefore identical. A release from either door lands in the same `consent_events` store and shows in the client's portal.
- **The link still reads nothing back (must not undo).** No prefill, no prior-provider list, no earlier releases. The signer types the patient's full name and date of birth; the server checks them against the record (`uploadLinks.roiIdentityMatches`: exact DOB, plus last name and first name or initial against legal and preferred names). A mismatch gets one sentence that never says which part was wrong. A record with no DOB on file is refused, not waved through.
- **Guessing is capped.** 5 wrong guesses per link per 24 hours locks the release form (`ROI_LINK_LOCKED`), checked before the comparison so even a right answer is refused while locked. 5 successful releases per link per day (`ROI_LINK_RATE_LIMITED`). Stamps live on the link row (`roiFailedAt`, `roiSubmittedAt`). Regenerating the link starts fresh; only the client or an admin can do that. The document checklist upload is not affected.
- **What prints on a link release:** the record's name and DOB (just proven), and only the address and phone the signer typed. The record's address and phone never reach the link page. The portal release still prints the record's identity as before.
- **The signer's copy (45 CFR 164.508(c)(4))** comes back in the submit response as PDFs, with a Save Copy button. A link signer may have no portal to fetch it from later. The page says it will not show them again.
- **Provenance.** `consent_events.channel` is `link` or `portal` (new field, beside `source`, so nothing that reads `source` changed). Link activity rows have `userId: null` and name the upload link.
- **Two guards repointed, not loosened:** `test/roi_rebuild.test.js` now reads the shared handler (and asserts the link uses `roiLinkPatientIdentity`); `test/impersonation.test.js`'s signature sweep skips `/api/gfc/upload/:token/…` with the reason that it reads no session, so it can never act as a viewed account.
- **Verified:** 4 new unit tests in `test/upload_links.test.js`; `scripts/verify_upload_link.js` 80/80 through the real routes (27 new checks); 8 of 8 mutations caught (identity skipped on submit and on scan, record address leaking, lockout skipped, DOB not compared, first name ignored, failures not counted, channel mislabelled); `scripts/verify_roi.js` 36/36; full suite green; the page driven in Chromium at phone width through fill, sign, submit and the copy button.
