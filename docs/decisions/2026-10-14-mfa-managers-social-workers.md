# Managers and social workers need 2FA on any account type (owner request, 2026-10-14)

Owner ask: "upgrade the managers and social workers to both require 2FA to maximize protecting from bad actor access."

- **What was true before:** both groups already got 2FA when set up through the User Management form, but only by accident of their account type. The form stores "Manager" as role `user` plus `isManager`, and a case manager as `caseManager`, and both of those are on `MFA_REQUIRED_ROLES`. The rule itself never looked at the manager flag or at the clinical role.
- **Three holes, now closed** (`mfa.js`, `config.js`):
  1. **Manager-level access on any other account type signed in with a password.** The lab-era service-portal manager (`vendor` + `isManager`), and either legacy flag the server admits through the same doors (`hasAdminHubAccess`, `hasClientPortalAdminAccess`), skipped 2FA. Those doors are the admin hub, `GET /api/users`, client-portal admin and the enrollment records. `mfa.MANAGER_LEVEL_FLAGS` now gates all three flags whatever the role.
  2. **A social worker's clinical role did not count on its own.** The check read the stored `hasClinicalAccess` flag and trusted it to be in sync. It now also asks `clinicalRoles.canClinicalRead`, so LCSW, LMSW, RN, provider and read-only all need 2FA on any account type, and a case manager with no stored role resolves to LMSW and is gated even with an empty role list.
  3. **One env var could switch it off for both groups.** `MFA_REQUIRED_ROLES` replaced the default, so setting it to `admin` silently dropped every clinician and case manager. `admin,user,caseManager` is now a floor (`MFA_REQUIRED_ROLES_FLOOR`): the env var can add a role, never remove one. There is no production reason to narrow it; `MFA_ENFORCE=false` is the dev escape hatch and is refused in production.
- **Not widened:** clients, family (POA included) and plain caregivers stay ungated, per the open owner decision. A service technician (`hasServicePortalAccess` without `isManager`) is not a manager.
- **Takes effect on the next request, not the next login.** `authenticateToken` already revokes a session that never passed MFA once its account becomes MFA-required (`AUTH_MFA_REQUIRED`). Anyone newly covered is signed out once and sets up an authenticator at their next sign-in. "View as" is unaffected: it inherits the admin's own verified session.
- **Must not undo:** a test sweeps the five server gates that admit manager-level access (`requireAdminHubAccess`, `requireClientPortalAdmin`, `requireEnrollmentStaff`, `requireEnrolledClient`, `GET /api/users`) and fails if one admits a flag `mfaRequiredFor` does not cover. Opening a new door to a new flag means adding the flag to `MANAGER_LEVEL_FLAGS`, or it becomes a password-only way in.
- **Verified:** 5 new tests in `test/mfa_sessions.test.js`, each case on an account type outside the role list so only the new rules can be what gates it; 6 of 6 mutations caught (manager flags dropped, clinical role dropped, env var replacing the floor, a gate admitting a new flag, over-widening to everyone, one flag dropped from the set). The floor is tested by loading `config.js` in a child process under four env values. One guard repointed, not deleted: `test/clinical_roles.test.js` read the single config line, which no longer exists in that shape; it now checks the resolved list and the clinical-role rule by behaviour. Full suite 2340 pass, 0 fail, 1 skipped (pre-existing). `scripts/verify_session5.js` 38/38 through the real server over HTTP (enrolment, verify, recovery codes, revocation, the real idle wait, audit rows). The live probes that sign in as managers are unaffected: they mint tokens directly or run with `MFA_ENFORCE=false`, and their managers are role `user`.
- **Open for the owner:** (1) if the deployment sets `MFA_REQUIRED_ROLES`, it can no longer narrow anything; check it is unset or only adds. (2) Whether clients, family POAs or caregivers should need 2FA is still open; `MFA_REQUIRED_ROLES=admin,user,caseManager,vendor` would add caregivers with no code change.
