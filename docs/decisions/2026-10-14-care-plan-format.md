# The care plan format: eight blocks, goal status, and care plans for home care clients (owner request, 2026-10-14)

Owner ask: build the "GFC Care Plan Format" document, with goals, interventions and status working "like the other fields" (typed in by a clinician; a later KaiCare integration fills the same fields, with no source labels or extra metadata). The owner also approved the review points: different required fields by service line, a caregiver-scope check, status kept out of the signed plan, escalation plugged into what the caregiver app already does, no diagnosis codes in the family view, and "outside the practice" started from intake.

- **One module, `carePlanFormat.js`, pure.** `clinicalRepository.buildCarePlanVersion` delegates to it. The plan now carries `problemItems`, `goalItems`, `interventions`, `medicationManagement`, `outsideCare`, `escalation` and `review`, beside the existing schedule fields (`eachVisit`, `visitFrequency`, `visitDays`, `visitTimes`, `duration`), which are unchanged.
- **`problems` and `goals` stay plain string lists, derived from the structured items at save.** Every older reader (portal summary level, pre-visit packet, patient publish, signed PDF of an old plan) keeps working. An old plan is SHOWN in the new shape (`structuredView`, `legacyFormat: true`) and never rewritten; a string goal becomes an object only when a clinician writes the next version.
- **Required fields by service line, one table (`REQUIREMENTS`).** Home care (PHC): a problem, a goal, an each-visit task, a visit frequency, a "call GFC when" sign, and a review cadence plus next review date. IHPC: problem prognosis and expected outcome, a measure and target on every goal, an intervention, who manages medications, escalation and review. BOTH is the union. Refused as `CARE_PLAN_INCOMPLETE` with `missing` and the labels in words. With no service line passed, only a problem and a goal are required, as before.
- **Goal status changes WITHOUT a new version.** `POST …/care-plan/goals/:goalId/status` (clinicians who can write plans: `requireClinicalWrite` + `CARE_PLAN_AUTHOR`). A new version needs new signatures; a status update must never send the family back to re-sign. Every change is its own row in `care_plan_goal_status_events` (new, PHI, registered); the current status sits on the goal with who and when. `GET …/history` lists them. The audit row names the goal and the status, never the note. Writing a new version carries each goal's status forward by goal id.
- **Every client can have a care plan, home care included.** The three care-plan routes use `loadCarePlanClient` (any client), not `loadClinicalClient`. This makes the existing "RN signature completes a home care plan" rule (`clinicalRoles.evaluateCarePlanSignature`) reachable for the first time. A home care client has no chart in the clinical workspace, so their plan opens at `/clinical?carePlan=<clientId>`, linked from the enrollment screen's new "Care plan" card. The inbox now looks at every client for a plan waiting on a second signature (an LMSW-authored home care plan was invisible).
- **Caregiver scope is advice, never a refusal.** `scopeWarnings` flags medication work assigned to a caregiver ("reminders only below LPN"), measurements (need a sign-off), skilled tasks, and "managed by caregiver". Returned as `warnings` on save and shown to the author. Whether a particular caregiver can do the task stays the visit log's decision.
- **Who sees what.** Patient and POA (portal full level): `patientProjection` (goals with progress, interventions in plain language, when to call, other care, who handles medicines, next review). Never prognosis, adherence concerns, internal ids or the raw blocks; the raw block names are not in `FILTER_MAP`. Family at summary level: the plain goal list and schedule, as before. Diagnosis codes are never typed into a problem: picking from the chart fills the plain title. Caregiver: tasks, schedule, interventions assigned to a GFC caregiver, and the escalation block.
- **A real bug fixed on the way: caregivers never saw their task list or schedule.** `caregiverClientView` read `tasks`, `frequency`, `days`, `times` off the plan, keys no saved plan has ever carried. `caregiverProjection` maps the real keys. (`authorizedTaskIds` still reads `plan.tasks` and was left alone on purpose: turning it on would start narrowing the visit-log form from free-text tasks.)
- **Read from the record, not retyped:** code status from intake's advance directive, last medication reconciliation from `medRecLast`. A new plan starts with pharmacy, hospital and outside providers from intake's medical team block.
- **The signed PDF prints the new sections and never prints goal status**, because status changes without a new version and a signed PDF would show a status that is no longer true. An old plan prints as before.
- **The author form starts from the current plan**, so a new version is an edit, not a retype (it used to open blank). Option lists come from the server (`vocabulary`).
- **Verified:** `test/care_plan_format.test.js` (27 tests) plus one caregiver test; 12 of 12 deliberate breaks caught (one survived first because the builder already refuses a plan with no problems, so a direct test of the requirements check was added). Full suite green. `scripts/verify_care_plan_format.js` 23/23 through the real HTTP routes (home care plan refused then saved, status without a new version, read-only case manager refused, status carried into v2, IHPC needs the clinical blocks and waits on a provider). The standalone page rendered in Chromium: view, status update and the pre-filled form, zero page errors. All four edited pages compile.
- **Not built:** the KaiCare integration (the fields are ready for it; no source labels by owner choice). Caregivers cannot update goal status (clinicians only, the default while the owner has not decided).
- **Open for the owner:** (1) the provider co-signature is captured but not printed on the signed care-plan PDF (pre-existing, not changed here). (2) Whether a caregiver should be able to mark a goal's status.
