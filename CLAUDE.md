  **It took three rebuilds, and all three failures were ours, not the operator's. Each one is a rule worth keeping:**
  - **A `404` from `raw.githubusercontent.com` is not proof a file is missing.** It negatively caches a path for a few minutes: a file that has just landed answers `404` by BRANCH NAME while the same content answers `200` by COMMIT SHA. Measured — 404 for about two minutes after the push, then 200, nothing changing in between. **09/2026 — Patient-link duplicate guard (identity safety) — ✅ merged (PR #50).** The link step POSTed a new OpenEMR Patient unconditionally, so every retry minted another chart for the same person — the eight duplicate `Demo Client` rows on the dev instance. `POST /api/clinical/patients/:clientId/link` now searches OpenEMR **before** creating:
- **Candidates are offered, never auto-linked.** A shared surname and date of birth is not proof of identity, and a wrong link writes clinical data into someone else's record. A match returns **409 `EMR_PATIENT_EXISTS`** with the candidates; the clinician links one or explicitly confirms a new chart with `{confirmDistinct: true}` (recorded on the activity entry as `confirmedDistinct`).
- **Match rules** (pure helpers in `clinicalRepository.js`, build-enforced in `test/patient_link_guard.test.js`): surname must always agree; `exact` = surname + given + DOB, `probable` = surname + DOB with a different given name (nickname/middle name), `possible` = surname + given where one side has no DOB. **A known but different DOB is never a match** — that is a different person. Names are folded for case, accents and punctuation (`O'Brien` = `OBrien`, `José` = `Jose`).

A client with no surname gets **409 `EMR_MATCH_NO_NAME`** rather than an unsearchable chart.
- **Also guards the existing-id path:** linking to an OpenEMR patient another app client already owns returns **409 `EMR_PATIENT_CLAIMED`**, so two app records can never point at one chart.
- Verified live against the dev instance: the seven remaining `Demo Client` rows are all returned as candidates (create blocked), while a genuinely new patient, a same-surname/different-DOB patient, and a nameless client each behave correctly. **The duplicate rows themselves are still on the dev instance and want deleting** — the guard stops new ones, it does not merge existing ones.
